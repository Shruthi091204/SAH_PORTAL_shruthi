# SAH Portal Security Remediation

Date: 2026-09-01

## Result

The repository now contains a production remediation for the critical and high-risk findings in both supplied assessment reports. The migration is data-preserving: registrations, teams, evaluations, and notifications remain. It only redacts historical plaintext credentials and locks/invalidate old OTP storage.

## Severity and disposition

| Finding | Severity | Remediation |
| --- | --- | --- |
| Plaintext passwords / exposed OTPs | Critical | Server-only `auth_otp_challenges` table stores SHA-256 OTP digests; old credential fields are redacted in place and old OTP tables lose all browser access. |
| Public account-takeover RPC | Critical | All legacy reset/OTP RPCs are revoked; password reset is performed only in the `auth-otp` Edge Function after OTP verification. |
| Public database reads | Critical | `profiles` is private, with a narrow authenticated `directory` view; privileged evaluation/panel data is RLS-gated. |
| Admin/judge enumeration | High | Private profile policy prevents anonymous access; only authorized roles can read sensitive profiles. |
| Browser-only authorization | High | Database RLS checks roles through `my_role()` and scope evaluation/panel access at the data layer. |
| Notification injection | High | Browser notification writes are disabled; recipient read/mark-read remains available. Notifications must be generated by a trigger or server-side function. |
| Shared admin credentials | High | Requires an operational change: create a distinct Supabase Auth user per organizer, then set each existing profile role to `admin`. |
| Realtime exposure | Medium | RLS applies; additionally disable replication for `registration_otps` and `password_resets` in the Supabase dashboard. |
| Missing browser policy | Low | CSP, clickjacking, object, and base URI restrictions are in `index.html`. |
| Hard-coded SMTP credentials (additional) | Critical | Removed from Vite/API/Edge Function fallbacks. Rotate the previously exposed SMTP password immediately. |

## Deployment order

1. Rotate the exposed SMTP app passwords and set `SMTP_USER`, `SMTP_PASS`, and optionally `SMTP_HOST` as Supabase Edge Function secrets.
2. In Supabase SQL Editor, run `supabase/migrations/20260901_security_hardening.sql` as one transaction.
3. Deploy `auth-otp` with `supabase functions deploy auth-otp --no-verify-jwt`. The function has its own rate control because password recovery and registration are intentionally public.
4. Deploy the frontend build. Its registration and password reset screens now call `auth-otp`; no browser code reads OTP tables or calls reset RPCs.
5. Disable Realtime replication for `registration_otps` and `password_resets`; review API gateway logs for prior notification abuse; create individual admin accounts and force password resets for all existing users.

## Post-deployment verification

- Anonymous REST reads of `profiles`, `password_resets`, `registration_otps`, `notifications`, `evaluations`, and panel tables return no rows or an authorization error.
- Legacy `reset_user_password_by_email`, `secure_reset_password`, and `verify_registration_otp` calls fail with permission denied.
- Registration verifies the college email and then permits a normal login.
- Password-reset requests return the same confirmation whether or not an account exists; a correct OTP works once and an incorrect/reused OTP fails.
- A student cannot read evaluations, write notifications, or obtain admin/judge profiles. A judge/admin can still use authorized workflows.

## Follow-up hardening

- Move every browser-created notification to a database trigger or narrowly authorized Edge Function before re-enabling that feature.
- Test team marketplace/profile views against the new private profile policy and use `directory` for any student discovery UI; do not re-open `profiles` to fix an UI error.
- Do not commit `.env`; use only the public Supabase URL/anon key in frontend environment variables.
